Build · what the model is

An LLM writes one token at a time, choosing from probabilities.

Probabilities are illustrative. A token is about ¾ of an English word; prices are quoted per million tokens.

I'll use Claude for examples; the ideas apply to any model. Start with the one thing a language model actually does. It reads text as tokens, pieces of words. [click] For the next position it computes a probability for every token in its vocabulary.

[click] It picks one, appends it, [click] and runs the whole thing again for the next token. That is all generation is: predict, pick, append, repeat.

Two consequences. Everything is priced and limited in tokens. And the output is sampled, so the same prompt can give a different answer next time. Keep that in mind when we get to evals. It also explains a classic weakness: the model sees pieces of words, so exact counting and arithmetic are better left to a tool.

Build · what the model is

It learns by reading, imitating and practising.

1

Read

Pre-training on internet-scale text. Language and facts.

2

Imitate

Fine-tuning on good examples, including agents at work.

3

Practise

Reinforcement learning. Rewarded when the result checks out.

After L. Robinson, Stanford CS146S "How always-on agents work" (34:33)

How does it get those probabilities? Three stages. [click] First it reads: billions of documents, always predicting the next token. That gives it language and a lot of facts.

[click] Then it imitates. People show it what a good assistant answer looks like, and now also what an agent working inside a tool like Claude Code looks like.

[click] Then it practises. It attempts tasks and gets rewarded when the result checks out. Notice that third stage needs a way to check the result. That idea comes back at the end of the talk.

Build · what the model is

The model is stateless, so every call starts from zero.

Legend: ■ instructions ■ conversation so far ■ new message

This is the most important technical fact of the talk. The model has no memory between calls. It is stateless.

[click] On the left is what you see: a chat that seems to remember. [click] On the right is what the model actually receives. Call one is the instructions plus your message. [click] Call two is the instructions, your first message, its first reply, and your new message, all sent again from scratch.

Think of a brilliant consultant with amnesia who rereads the entire project file before every meeting. It is also why a long chat gets slower and more expensive: every turn re-sends everything before it. Everything that follows, harnesses, caching, memory, exists because of this one fact.

Build · context engineering

  
Caching matches the prefix exactly, so one changed byte re-bills everything after it.

  

  
"Prompt caching is prefix matching. Any change anywhere in the prefix invalidates everything after it." Shihipar, claude.dev, 2026. Cache read 0.05× base price on Opus 5.5 (Anthropic pricing).

  

    
Remember the model is stateless and the whole stack is re-sent every turn. That would be ruinous without caching. [click] Turn one: everything is new and paid in full, in orange. [click] Turn two: everything already seen is a cache hit, in green, at a twentieth of the price on Opus 5.5. Only the new message is orange. [click] Turn three, same again. The green part grows, the orange part stays small.

    
[click] Now turn four, in two alternative versions. Version A: someone edits the instructions at the top, say by putting the current time in them. The match is exact, from the first byte. Everything below the edit turns orange and you pay full price for the whole stack.

    
[click] Version B, same turn four: the edit is near the bottom, and only the tail is re-paid. So: never touch the top. It is a familiar systems trade-off: design the stable part once, and make only the variable part pay.

So how does a harness keep its hit rate so high when things change all the time? It adds, it never edits. [click] When the date or a file changes, the harness appends a small reminder to your newest message instead of editing the instructions. [click] Tools you rarely use stay as name-only stubs, so the tool list never changes shape. Under the hood, the API lets a harness mark up to four cache breakpoints, so tools, project files and conversation are cached as separate tiers and a change only invalidates the tiers after it.

a score you trust · cheap tries · many of them

      
SKIP IT FOR
taste · one-off decisions · scores you can't check

Third part: improve. This is optimisation from 40.002 again, local search, except the decision variable is your prompt. [click] The loop is short. Change one thing, a sentence in the prompt or the model you use. Run your evals. If the score went up, keep it; if not, revert. Repeat, often hundreds of times, with an agent doing the trying. [click] It fits when you have a score you trust, tries are cheap, and you can afford many of them. [click] It does not fit taste, one-off decisions, or any score you can't check, because the agent will happily climb the wrong hill.

Improve · hill-climbing

  
Products improve in two loops, and evals expire.

  

  
Fix loop and model loop: L. Robinson, CS146S (36:07–37:04), who calls them inner and outer. "Don't assume the new model is always better": Kun Chen, 2:18. Re-do evals every ~6 months: my LinkedIn series (claudetober), Day 18.

  

    
Zooming out to how the companies building these products work. [click] A fix loop runs daily: the agent gets something wrong, that failure becomes an eval, someone fixes the prompt or the harness, the eval confirms it, and it ships.

    
[click] A model loop runs every few months: a new model is trained, partly on those failures, and dropped in. Lee's team works on the assumption that today's model is the worst one they will ever use.

    
[click] Two consequences for you. Evals expire, so redo them about every six months. And as Kun Chen says, do not assume the new model is better for your task. Measure it with your evals.
